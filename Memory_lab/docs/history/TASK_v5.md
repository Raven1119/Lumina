# 任务卡 v5（/goal）：切换到 flash、打通联想、低成本评测

**目标：** 一次做完以下四个阶段，中途不要停下来问仓库主人。

1. 所有模型调用改用 DeepSeek v4.1 flash，已经做过的评测不重跑。
2. 按 `docs/DESIGN_v5.md` 升级记忆，打通联想：Dream 归纳规律、按意外程度挑选联想位、回复前先想一下。
3. 按设计文档降低评测成本：取消影子回答，“用上”判断并入整合，盲评只附证据，第二遍只评有偏好的条目。
4. 用新的最终配置 P7 做一次评测，写报告并提交。

设计细节以 `docs/DESIGN_v5.md` 为准。新提示词已提供：`prompts/integrate_v3.md`、`prompts/pattern_v1.md`、`prompts/answer_v4.md`，不要改动。任务卡和设计文档没写清的地方，自己选合理做法，写进报告的“偏差”一节。

## 0. 约束

- **预算：** 累计新增输入不超过 300 万 token；超过就停下，写报告说明原因。每个阶段开头打印预计的调用次数，结尾打印实际数，都按用途分列。
- **不重跑：** v4 的所有记忆层结果、回答和盲评，都直接作为基线，不重新生成。保留集已经用过，不再运行。
- **不修改：**
  - `core/` 和仓库其他目录；
  - `eval_set/scripts/`、`eval_set/gold/`、`eval_set/build.py`；
  - 已有的提示词文件。
- **新功能都要有离线测试，原有测试全部保持通过。**
- **提交：** 所有改动做本地提交。推送只推 `docs/TASK_v5.md`、`docs/DESIGN_v5.md`、`docs/RESULTS_v5.md` 三个文档（沿用既定规则），每个阶段完成后推送一次。
- `RESULTS_v5.md` 必须自成一体（见 §5），仓库主人和 Claude 只看这份报告。

## 1. 阶段 1：切换模型

- 实验室的模型名改为可配置：`LUMINA_MEMLAB_MODEL` 环境变量，或 `--model` 参数。默认值为 DeepSeek v4.1 flash 在 API 中的准确名称，由你查 DeepSeek 文档或 models 接口确认，并写进报告。
- 不再从 `core/model_client.py` 导入 `DEEPSEEK_MODEL`。所有用途都改走新的配置，包括整合、归纳、摘要、回答、评审和审计。
- 缓存键中含有模型名；旧的 pro 缓存保留不动。
- 用 1 条真实调用验证：模型名可用，响应能正常解析。

## 2. 阶段 2：记忆升级（设计文档 §3–§5）

1. **Dream 归纳**（§3）：
   - 挑选候选组（共现、前后关系、情形相似），去重，至多 6 组，每组覆盖 ≥ 2 个逻辑日；
   - 调用 `pattern_v1`，用途为 `pattern`；
   - 按 text、existing、none 三种结果应用，每组生成规律前由程序复核逻辑日；
   - 解析失败时只跳过这一步，不影响本次 Dream 的其他部分。
2. **按意外程度挑选联想位**（§4）：
   - 平时激活 ā 按“快照版本 + 逻辑日”缓存；
   - lift 用 ε 平滑，并执行候选条件；挑不出合格的就留空；
   - 只给这一条渲染原因。
3. **回复前的“想起”**（§5）：用 answer_v4，按 §5.2 解析，把“想起”那一行记入 `answer.noticed`。
4. **新预设 P7**：参数见 §9。旧规则保留为可选项，旧预设的行为不变。
5. **离线测试至少覆盖：**
   - 候选组的三类条件、去重、逻辑日约束和上限；
   - 规律记忆的继承、merge 边，以及实例不被修改；
   - existing 和 none 两种结果；
   - lift 的计算、平滑和候选条件，以及留空的情况；
   - answer_v4 的解析、重试和回退；
   - 旧预设的召回结果逐字节不变。

## 3. 阶段 3：降低评测成本（设计文档 §6–§7）

1. **取消影子回答**（§6.1）：“用上”判断所看的回复，改用剧本中紧随其后的林素台词（`usage_reply_source=scripted`）。影子回答保留为可选项，默认不用。
2. **“用上”判断并入整合**（§6.2）：
   - 使用 integrate_v3，按设计文档渲染 `{{recalled}}`，记忆正文只列一次；
   - 校验 `used` 字段，应用强化和共同召回；
   - P7 不再发出单独的 `usage` 调用。
3. **盲评 v2**（§7.2）：
   - `judge/build_packets.py` 增加证据包模式，每条附三部分证据，至多 40 轮；
   - `judge/judge_prompt_v2.md` 由你根据 v1 改写，打分定义不变，只改对证据的说明和“说错往事”的判定口径；
   - 每批 10 条；
   - 回答逐字相同的条目，直接记为平局，不送评；
   - 第二遍只评第一遍有偏好的条目；
   - 汇总脚本兼容这种“部分第二遍”。
4. **反事实核对**（§7.1 的 0+ 层）：在本地 v4 P6d 的运行结果上，纯本地重算召回，不调用模型。要回答两个问题：
   - 联想位换了人的探针有多少；
   - 新旧两条分别是否命中金标准，其中 6 条远联想探针（A11、A12、A13、B11、B12、B13）的目标是否进入联想位或前 20。
5. **离线测试至少覆盖：**
   - `{{recalled}}` 的渲染和去重；
   - `used` 的校验和强化；
   - 剧本台词作为回复来源；
   - 证据包的组成和上限；
   - 相同回答跳过评审；
   - 部分第二遍的汇总；
   - 不再发出单独的 usage 调用。

## 4. 阶段 4：评测并提交

全部使用 flash，每项只运行一次。

1. **P7 回放（真实调用）：** 在 dev_a、dev_b 上各跑一次完整回放。这一次同时产出三样东西：
   - 记忆层 suite；
   - 全部规律记忆；
   - 35 条主探针的 answer_v4 回答，带滚动摘要。
2. **定向核对（第 1 层）：** 用 P7 同一份记忆，对下面这些探针再生成一份 answer_v2 回答，与 answer_v4 并排列出。只列原文，不评审。这一项用来看“想起”这一步单独带来了什么。
   - A01、A06、A11、A12、A13、A27
   - B01、B04、B11、B12、B13、B28
3. **最终盲评（第 2 层）：**
   - 用盲评 v2，比较 P7（flash）和 v4 的 P6d 回答（pro，直接复用）；
   - 两个开发集，共 70 条；
   - 轮次名为 `v5_P6d_pro_vs_P7_flash`；
   - 按 v4 的采纳规则（N=7，E=2 个百分点）判定；
   - 报告中注明：两边的差别里混有模型本身的差异，而且评审模型没有重新校准。
4. **提交：** 所有改动做本地提交，按 §0 推送三个文档。

## 5. `RESULTS_v5.md` 必须包含

1. **执行情况：** 每个阶段做了什么；按用途分列的调用次数和 token 数；偏离任务卡的地方。
2. **模型：** 确认的 API 模型名，以及那 1 条验证调用的结果。
3. **规律记忆：** 两个集合写出的全部规律，逐条列出正文、所连的实例（ID 和正文摘要）、候选类型，以及它们覆盖的日子。另外列出被判为 none 的组的数量，以及几个例子。
4. **联想位：**
   - 反事实核对的统计表；
   - P7 回放中，6 条远联想探针的目标各排在第几、有没有进入联想位；
   - 联想位的原因文本示例。
5. **“用上”判断：**
   - 每个窗口进入上下文的记忆次数与判为用上的次数，以及总比例；
   - 10 个随机例子（记忆正文、剧本回复、判断结果）；
   - 不合法条目的数量。
6. **记忆层指标：** P7 与 v4 P6d（pro）的淡忘 +60、保留 +60、cue、@1、@3、MRR 对照表，并注明模型不同。
7. **定向核对：** 12 条探针的 answer_v2 和 answer_v4 回答原文，以及 answer_v4 中“想起”那一行。
8. **最终盲评：**
   - 汇总表：一致胜、一致负、平、不一致、说错率、活人感、符号检验 p、按噪声带的判定；
   - 按类别的胜负表；
   - 全部非平局条目：探针 ID、类别、偏好、一句话理由；
   - 全部被标为“说错往事”的条目及理由。
9. **成本对照：** 本任务每种用途的 token 数，与 v4 对应部分的比较。
10. **滚动摘要截断统计**（设计文档 §10）：只统计，不修复。
11. **最后一节：**
    - 联想三个环节各自是否打通，每项附证据；
    - 仍未解决的问题，每条附证据；
    - 下一步建议，只写有证据支持的。
